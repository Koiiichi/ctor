UML CHANGES REQUIRED BY THE SPECIFICATION
=========================================

The UML diagram (uml-1.png) has not been edited. Every divergence between the
implemented code and the diagram is recorded below, with the specification
section that forced it. Where the specification and the UML disagreed, the
specification won.


1. Player::loseHalfToGeese (DONE)
   UML:  int loseHalfToGeese()
   Now:  std::vector<int> loseHalfToGeese()
   Spec: 3.6 Moving Geese

   The spec requires printing one "<numResource> <resourceName>" line for each
   resource type lost. A single int reports only the total, so the caller cannot
   produce that output. The vector holds per-material counts in the order
   brick, energy, glass, heat, wifi; the total is its sum.


2. Player::stealFrom (DONE)
   UML:  void stealFrom(Player& victim)
   Now:  Material stealFrom(Player& victim)
   Spec: 3.6 Moving Geese

   The spec requires the line "Builder <colour1> steals <resource> from builder
   <colour2>." A void return gives the caller no way to name the resource.
   Precondition: the victim must hold at least one resource. Interface only
   offers victims whose total is non-zero, as the spec's candidate list
   ("have a non-zero number of resources") already requires.


3. Player::buildResidence (DONE)
   UML:  bool buildResidence(int vertex)
   Now:  bool buildResidence(int vertex, bool beginning)
   Spec: 3.1 Building Residences, 4.1 Beginning of Game

   Spec 3.1 gives two conditions for building a residence: no adjacent
   residence, AND "it is either the beginning of the game or they have built a
   road that is adjacent to the vertex". The opening basements of 4.1 are also
   placed without paying resources. The flag distinguishes the two cases.


4. Map::canBuildResidence (DONE)
   UML:  bool canBuildResidence(int vertex, Player *p)
   Now:  bool canBuildResidence(int vertex, Player *p, bool beginning)
   Spec: 3.1 Building Residences

   Same rule as above. The previous implementation enforced only the adjacency
   condition and allowed a residence anywhere on the board, which is the second
   condition of 3.1 going unchecked.


5. Vertice::buildSettlement (DONE)
   UML:  bool buildSettlement(Player *owner)
   Now:  bool buildSettlement(Player *owner, bool freeBuild)
   Spec: 4.1 Beginning of Game

   The two opening basements are chosen, not purchased; 4.1 describes no cost
   and a builder starts with no resources, so charging would make the opening
   impossible. freeBuild skips the cost check and deduction only.


6. Player::getBuildingPoints  (new member, not on the UML) (DONE)
   Now:  int getBuildingPoints() const
   Spec: 2.7 Builders, 4.4 End of Game

   2.7 requires printing "<numPoints> building points" in a builder's status and
   4.4 ends the game at 10 or more. The UML has a private buildingPoints field
   but no accessor, so neither was reachable from outside Player. Computed from
   the builder's settlements rather than stored, so it cannot drift out of sync
   when a residence is improved.


7. Map::getGooseTile  (new member, not on the UML) (DONE)
   Now:  int getGooseTile() const
   Spec: 3.7 Saving a Game, 3.6 Moving Geese

   3.7 requires the saved file's last line to be the tile index holding the
   geese. 3.6 forbids replacing the geese on the tile they already occupy.
   Map stored the goose as a Tile* with no way to recover its index.


8. Interface  (class present on the UML, members never specified) (DONE, false alarm, already handled in existing case)
   Spec: 4 Gameplay, 5 Command-line Interface

   Implemented with the private members and helpers listed in interface.cc.
   The UML shows the class but not its contents, so this is an addition rather
   than a contradiction. Public surface is only the constructor
   Interface(int argc, char *argv[]) and void play().


9. Edge::build (DONE)
   UML:  bool build(Player *owner)
   Now:  bool build(Player *owner, bool freeBuild = false)
   Spec: 3.7 Saving a Game, 4.1 Beginning of Game

   Restoring a saved game must reproduce the roads exactly as written, not
   re-purchase them. build unconditionally charged 1 HEAT and 1 WIFI, and the
   save file restores resources after the roads, so every road in a loaded game
   failed its cost check and was silently dropped. freeBuild skips the cost
   check and deduction only, mirroring Vertice::buildSettlement (change 5).
   The default argument leaves every normal build call unchanged.


NOT CHANGED, WORTH FLAGGING 
---------------------------

Dice::roll was made virtual with a virtual destructor, LoadedDice::roll made
public, and the const qualifier dropped, before this pass. Those correct plain
defects rather than contradict the diagram: without virtual, dispatch through
Player's unique_ptr<Dice> would never reach the subclass. (DONE, false alarm, already handled in existing case)

Settlement has no back-pointer to its vertex, so Interface derives the vertex

EXTRA CREDIT FEATURES
---------------------

Everything above records a place where the specification forced the code to
diverge from the UML. Nothing in this section does. These two features are
additions on top of a complete implementation; the specification neither
requires nor mentions either of them, and neither corrects a defect. They are
recorded here so the diagram stays reconcilable by the same process, not as
further numbered entries, which would misrepresent why they exist.


SHARED TOGGLE

Both features sit behind one switch, a private bool on Interface
(bonusEnabled, default false). The guidelines require an enhancement to be
selectable by a command-line flag on the same binary rather than a separately
compiled version, and then say that it would be even better if the
enhancements could be turned on and off dynamically while the program is
running. The better version is what is implemented, so the switch has two
controls:

  -enablebonus              command-line flag, parsed in Interface's
                            constructor alongside -seed / -load / -board /
                            -random-board. Sets the starting value only.
  enable-bonus              during-turn command, sets the bool to true.
  disable-bonus             during-turn command, sets the bool to false.

The two commands are recognised unconditionally, whatever the bool currently
holds and whether or not the flag was passed. Gating them behind the bool they
control would make it impossible to switch either feature on at runtime. Both
are listed in the static help text, unconditionally, like every other command
in that list.

With the bool false, neither feature is observable. "bank" falls through to
"Invalid command." like any other unrecognised word, and building-point totals
are computed exactly as they were before either feature existed.


FEATURE 1: BANK TRADING

A fixed-ratio trade against the bank, with no second builder involved.

  Command:  bank <give> <take>
  Ratio:    4:1. Four of <give> are deducted, one of <take> is added, both on
            the builder whose turn it is.
  Phase:    during the turn, the same phase as "trade".

There are no ports or variable ratios. The board model has no concept of a
port and inventing one would need adjacency data with no basis in the spec.

Reused rather than duplicated:
  - parseMaterial, the same <give>/<take> parsing "trade" already uses.
  - materialCode, to index the vector from Player::giveMaterialAmount.
  - Player::reduce and Player::increase for the transfer. No new method was
    added to Player, Map, Vertice or Edge.
  - "You do not have enough resources.", the string already used elsewhere for
    exactly this situation, printed when the builder holds fewer than four of
    <give>.

Success prints one line in the register of the existing trade output:
"<Colour> trades four <GIVE> to the bank for one <TAKE>."


FEATURE 2: LONGEST ROAD BONUS

The builder holding the longest continuous chain of their own roads gets a
bonus on their building-point total, and loses it when another builder
overtakes them.

  Minimum qualifying length:  5 roads (edges)
  Bonus:                      +2 building points
  Command:                    none

Longest road for one builder is the longest simple path through that builder's
own edges: no edge is reused, the path may run through a vertex that is empty
or that holds that same builder's own residence, and it is blocked from
continuing through a vertex holding another builder's residence. That blocking
rule is part of what "longest road" means in the real game and changes the
answer in ordinary board positions, so it is implemented rather than skipped.
The search is a plain depth-first backtrack over the builder's own edge
subgraph, run from every vertex. At 72 edges this needs no optimisation.

The bonus transfers only on a strict excess: a new builder must be strictly
longer than the current holder's recorded length to take it, so a tie leaves
it where it is. With no holder, the first builder to reach 5 takes it. This
matches the real game and stops the bonus flickering between builders on ties.

Reaching 10 or more points because of the bonus wins the game, as it does in
the real game. There is no special case suppressing that.

State lives on Map, not Player: Map owns every Edge and can therefore see
every builder's roads, while Player has no way to see another Player's state.
Map holds the current holder and the length that earned it, both private. The
holder is recomputed after a successful build-road in Interface::duringTurn
and after a load restores roads, not on every query, since a new road is the
only thing that can change it.

Player::getBuildingPoints asks Map through the reference Player already holds
and adds 2 when Map says this builder holds the bonus, but only when the
shared bool is true. That is how a feature with no command of its own is
gated: with the bool false the check is skipped and the total is exactly what
it was before. Map does not store its own copy of the enabled state and does
not know about Interface. Interface holds the authority and passes the current
value down; Map is only ever asked who the holder is.

DEFECTS FOUND BY THE TEST SUITE
-------------------------------

The suite in tests/ derives its expected output from the specification rather
than from this program, and found five behaviour defects. All five were fixed
inside existing function bodies. None of them changed a signature, so none of
them is a numbered entry above and the diagram needs no further edit for them.
They are listed here so a later reader can see they were considered.

D1. The second opening basement paid no resources.
    Spec: 1.1 Gameplay Overview, 4.1 Beginning of Game
    "The player gets a resource for each resource tile that their second
    residence touches." The opening built both basements free of charge and
    paid nothing for either. The first basement correctly pays nothing.
    Fix: Interface::grantSecondBasement, a new private helper called for the
    last four placements. It walks Map's tiles, skips PARK (2.2 "The PARK tile
    produces no resources") and calls Player::increase once per touching tile.
    Interface's members are not on the diagram (change 8), so nothing to edit.

D2. The saved <curTurn> named the current builder, not the next one.
    Spec: 3.7 Saving a Game
    "<curTurn> is the identity of the builder whose turn it will be when the
    game starts ... it ends the current player's turn and marks the next
    player as the one whose turn will start." saveGame wrote curTurn.
    Fix: write (curTurn + 1) % 4. The live game is not advanced by a save.

D3. With no -board argument the board was randomly generated.
    Spec: 3.5.5 Tile Distribution
    "By default, the file that is read is named layout.txt from the current
    directory. (If the file isn't present, the player needs to use the
    -random-board command-line argument.)" A random board was generated
    instead, so a plain ./constructor ignored the layout.txt the course
    supplies. Fix: Interface::setUpBoard reads layout.txt unless -board names
    another file or -random-board is given without a layout.

D4. ENERGY was drawn one column to the right of the reference rendering.
    Spec: 2.2 Tiles, and the supplied rectangular_layout.txt
    Material names were always placed at a fixed offset, which centres the
    four and five letter names correctly but puts the six letter ENERGY one
    column off. Fix: Map::display centres the name in the nine column cell,
    biasing the extra space to the right, which reproduces all six names.

D5. Interface::loadedGame was declared and never used.
    Not a specification matter. Removed, matching the earlier removal of the
    dead field on Player.

Two further behaviours were left alone deliberately. The help text at the
"during the turn" phase is the exact list from 4.3 again; the three bonus
commands are appended to it only while the bonus switch is on, so with the
switch off the output is byte for byte what 4.3 requires. And the geese are
drawn on the board from the start, which 3.7 explicitly permits ("It is up to
you whether they are initially displayed or not before a 7 is rolled") even
though the supplied rectangular_layout.txt does not draw them.
